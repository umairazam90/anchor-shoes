# Anchor Shoes: project brief

Owner: Umair. Pakistan-based seller of pre-loved shoes (TikTok, Instagram, Facebook Marketplace, OLX). Pairs are one-off, so stock is 0 or 1 per pair.

## Decisions (do not revisit without asking)
- Brand: **Anchor Shoes**. No anchor symbol anywhere in the branding. Logo A (Lace Frame) is the header logo, B (Seal) the profile picture, C (Sticker) for stickers and boxes.
- Palette: navy #17223B, brass #B8923F, deep brass #8A6D25 (text), light brass #D4B876 (on navy), cream #F7F5F0. Never pair red with green (navy for success, red #A3321F only for errors). Poppins for the site (self-hosted via @fontsource).
- Look (revised 2026-11-18): Umair did not like the first plain theme and asked for a **Shopify-store style**: announcement bar, sticky header with search/account/saved/cart icons, hero, size tiles, product cards with heart and quick-add, filters and sort, cart drawer, sticky buy bar on mobile. Keep it clean and simple for a not-very-modern audience.
- English only. Android only for alerts (no iPhone work).
- Customer flow (Umair's workflow): Home with **main categories by size** -> size-range page (e.g. EU 43-44) -> **sub-category = exact EU size** catalogue -> shoe page with details -> cart/checkout (order page) -> Contact page -> Track page. Plus search, saved pairs and a lightweight account.
- **Shop by brand (added 2026-11-20):** `/brands/` lists brands, `/brand/<slug>/` shows one brand's pairs with a size bar (EU size pills) above the grid. Brands come from each pair's `brand` field; nothing to maintain separately.
- **Photos are never cropped (2026-11-20):** every photo box uses `object-fit: contain`, centred. Photos are 4:5; other shapes sit centred with a neutral background. Do not switch back to `cover`.
- **Payment wording (2026-11-20):** the pair's price is cash on delivery, but **delivery charges are paid in advance** (shown on cart, order page, shoe page, return policy, WhatsApp order text). The order page must keep saying so.
- **No "Sent by TCS" / "Delivered by TCS" / "we call you" wording** on the storefront. How it works is exactly: Pick your pair -> Confirm the order -> Pay on delivery. TCS is only mentioned on the Track page (tracking number + link to TCS).
- **Self pickup** (`settings.pickup`, Main Peshawar Road, Rawalpindi) is shown on the Contact page only. Never on the home page.
- Return policy: generic page at `/returns/` (window from `settings.returnWindowDays`, currently 3, a placeholder Umair has not confirmed). Short version on each shoe page comes from `settings.returnPolicy` (`{days}` is replaced).
- Categories are EU size ranges in `src/data/categories.json`; sub-categories are the exact EU sizes that have pairs (generated).
- Cart exists (a pair can be in the cart once). Cart, saved pairs and account details live in the browser's localStorage (`anchor.cart`, `anchor.wish`, `anchor.me`). **No passwords.** Account = saved delivery details + saved pairs + order lookup by TCS number.
- Orders: customer orders, Umair confirms by call and WhatsApp, ships by TCS with COD only.
- **Checkout is an interim stub until M2**: with a WhatsApp number set it opens WhatsApp with the order text; without one it shows a "preview only, nothing was sent" panel. It does not reserve stock.
- **TCS tracking has no API.** Admin stores the TCS tracking number per order. The customer gets the number plus a link `/track/?n=<number>`; the page shows the number and sends them to the TCS website. Do not integrate TCS APIs.
- WhatsApp and call numbers are settings (defaults in src/data/settings.json, **edited in /admin/settings/** and stored in D1), never hard-coded. Both are set to Umair's real number **+92 311 9362391** (provided 2026-11-20).
- Never put an invented or placeholder phone number in the repo: a fake wa.me link could message a stranger. Only numbers Umair gave us.
- No Telegram. Alerts by email and Android push (tool to be chosen in M3).
- **Admin (phase A built 2026-11-20, branch `admin-panel`, see SETUP-ADMIN.md):** Cloudflare Access (Zero Trust) email one-time PIN in front of `/admin` and `/api/admin/*`, and the Worker **also verifies the Access JWT itself** (`src/lib/access.ts`, jose, checks issuer + audience + email, optional `ADMIN_EMAILS` allow-list). It **fails closed**: with `TEAM_DOMAIN`/`POLICY_AUD` empty every admin route returns 503. Writes also need a same-origin `Origin` header (CSRF guard). `DEV_ADMIN_EMAIL` (in `.dev.vars`, never committed) signs you in on localhost only. Umair first logged in with his own email and an emailed code (no password to store); **superseded 2026-11-21 by the email + password login in the next bullet.** **Access path rules need a domain on Cloudflare** (a bare workers.dev address can only protect the whole Worker, which would lock out customers). Fallback if Access is not wanted or no domain yet: custom login (more code and risk), not built.
- **Admin sign-in: email + password (2026-11-21, branch `password-login`):** Umair asked to sign in with an email and password instead of the Cloudflare Access emailed code. `/admin/login/` is a form on the site itself. Admins live in D1 (`admins` table, migration 3): **PBKDF2-SHA256 hash** with a random salt (100,000 rounds by default, `PASSWORD_ITERATIONS` variable overrides it; the count is stored inside each hash), sessions are a random cookie (`__Host-anchor_admin` on https; HttpOnly, SameSite=Lax, 14 days) of which **only a SHA-256 is stored** in `admin_sessions`, so changing a password or removing an admin signs them out at once. Wrong-password limits (`src/lib/guard.ts`, rules in `adminauth.ts`): each attempt is counted before the password is checked, 8 per account and 15 per address per 15 minutes, locked even for the right password; unknown emails cost the same time as real ones. **Admins are managed in /admin/admins/** (add, remove, change own password; max 200 characters, min 10). **Recovery has no email**: a Cloudflare **secret `SETUP_CODE`** (16+ characters, set in the dashboard, never in the repo) switches on `/admin/setup/`, which creates an admin or resets a password; with no `SETUP_CODE` that page is off. 5 wrong codes per address per 15 minutes. **Cloudflare Access is still accepted** (a valid Access token signs you in, as before), so it is the break-glass if everyone is locked out, but the Access application in Zero Trust must be **deleted or disabled** for the custom domain, or the emailed code still comes first. **CPU caveat:** the Workers Free plan allows 10 ms CPU per request and 100,000 PBKDF2 rounds took about 18 ms in Node, so on Free the login may fail with Cloudflare error 1102; fix = Workers Paid (preferred) or a lower `PASSWORD_ITERATIONS` (set it BEFORE creating the password, then run /admin/setup/ again). Not yet checked on Umair's real plan. Local test: `DEV_ADMIN_EMAIL` signs you in on localhost only, so open **http://0.0.0.0:4321/admin/** to see the real login (tests: `tests/password.test.mjs`).
- **Live catalogue (2026-11-20):** pairs and settings live in D1 and are read on every request (the storefront is on-demand rendered, so marking a pair sold shows at once). `src/data/products.json` is now only the **demo seed** inserted on the first run (flagged `sample`), and the fallback when no database is bound. Do not edit it to change the live shop; use /admin.
- **EU sizes can be thirds (adidas 42 2/3):** always print with `euText()`, build URLs with `sizeSlug()` (`42-2of3`), and use `inRange()` (a category's `to` is its last half size, so it covers up to `to + 0.5`). Never print a raw `p.size.eu`.
- **Flaws are required** in the admin (type "None" if none): honest condition is the brand promise.
- **Customer reviews (2026-11-21, merged to `main` the same day):** section at the very end of the home page (`#reviews`): rating summary + the latest 9 approved cards + a "Write a review" form (1-5 stars, name, optional city, comment 10-600 letters, up to 3 photos shrunk in the browser). **A new review is pending until approved in /admin/reviews/** (pre-moderation: the form is public and takes photo uploads). **Never seed fake or demo reviews** (honest condition is the brand promise). Guards on `POST /api/reviews/`: same-origin, hidden honeypot field, links and phone numbers refused, photos checked by file signature (3 max, 2 MB each), 2 per hour and 4 per day per sender (SHA-256 of IP + date, wiped once a person moderates the review), at most 60 waiting. Review photos live in R2 under `reviews/` and are deleted with the review. Rejecting = deleting. Not built yet: an alert when a review arrives (the admin's Reviews link shows the waiting count; email/push is M3 phase B), a CAPTCHA (Cloudflare Turnstile, add in M4 if spam shows up), an all-reviews page (home shows 9).

## Stack
Astro 7 (**on-demand rendering**, `@astrojs/cloudflare` 14) + TypeScript on a Cloudflare Worker (wrangler.jsonc; the adapter supplies the entry and the static-assets folder). **D1** (`DB`: pairs, settings; later orders and stock) and **R2** (`PHOTOS`: uploaded photos). Bindings are read with `import { env } from "cloudflare:workers"` and only inside `src/lib/db.ts`. Cloudflare builds from GitHub on every push, so no Cloudflare keys are shared with Claude: **the admin is tested locally in the Workers simulator (`npm run build && npm run preview`). Workers Builds of the `admin-panel` branch is green (2026-11-20) after `session: false` in astro.config.mjs (the adapter otherwise adds an unused SESSION KV store; the first branch build failed with it, cause not confirmed because the build log is only in the dashboard). The admin was verified live on 2026-11-21 (Access sign-in with the Cloudflare login method, photo upload to R2, saving a pair to D1) on anchorshoes.com.** Do not use `wrangler types`: its generated types clash with the browser types; `src/lib/cf-types.ts` declares the few D1/R2 methods we use.

## Code map
- `src/middleware.ts`: (1) serves `/img/*` photos from R2, (2) guards `/admin*` and `/api/admin/*` (Access token or login cookie, else redirect to `/admin/login/` or 401; Origin check; `no-store`, `noindex`, not framable; only login/setup pages and their two forms are open), (3) loads the shop snapshot into `Astro.locals.shop` for every storefront page.
- `src/lib/db.ts`: **the only file that touches D1/R2**: schema (`MIGRATIONS`, created on first use; to change tables ADD a new entry, never edit an old one), demo seed, `loadShop()`, admin pair/settings queries.
- `src/lib/shop.ts`: pure helpers (`rs`, `sizeSlug`, `inRange`, `brandSlug`, `sizeLine`) and `makeShop(products, settings)`, which builds the per-request snapshot (`available()`, `productsIn()`, `allBrands()`, `waLink()`, `catalogItems()`...). Pages do `const { ... } = Astro.locals.shop;`.
- `src/lib/validate.ts`: validation of pairs and settings (shared rules, whitelisted keys). `src/lib/access.ts`: Cloudflare Access token check (pure, unit-tested in `tests/`). `src/lib/password.ts` (hashing, password rules, tokens; pure) and `src/lib/adminauth.ts` (emails, cookie, safe redirect, limits; pure), `src/lib/guard.ts` (attempt counting). Login pages `src/pages/admin/{login,setup,admins}.astro`; APIs `src/pages/api/admin/{login,logout,setup,password}.ts` and `admins/`.
- `src/pages/catalog.json.ts` -> `/catalog.json`: live catalogue used by cart, search, saved pairs (items carry `euLabel`).
- `src/pages/admin/` (pairs list, `pair/[slug]` add/edit with `new`, `settings`), `src/pages/api/admin/` (pairs, upload, settings, samples), `src/layouts/Admin.astro`, `src/styles/admin.css`, `src/scripts/admin.ts`. Admin API URLs need the trailing slash (`trailingSlash: "always"`).
- Reviews: `src/lib/reviews.ts` (pure rules and helpers, unit-tested in `tests/reviews.test.mjs`), `src/pages/api/reviews.ts` (public submit), `src/pages/admin/reviews.astro` + `src/pages/api/admin/reviews/[id].ts` (moderation), `src/scripts/reviews.ts` (the form), `Stars`/`ReviewCard` components. Table `reviews` is migration 2 in db.ts. The form's hooks use the `data-rev-*` prefix on purpose: plain `data-add` belongs to the cart buttons in store.ts.
- `src/scripts/store.ts`: cart, saved pairs, drawers (menu/cart/search), announcement rotation. Imported by `Base.astro`.
- `src/components/`: `ProductCard`, `ShopGrid` (filters + sort, client-side), `Crumbs`, `Icon`.
- Pages: `/`, `/shoes/`, `/size/<range>/`, `/size/<range>/<eu>/`, `/brands/`, `/brand/<slug>/`, `/shoe/<slug>/`, `/cart/`, `/checkout/`, `/search/`, `/wishlist/`, `/account/`, `/contact/`, `/track/`, `/size-guide/`, `/returns/`, 404.
- `src/lib/sizes.ts`: brand size charts (Nike/Jordan, adidas) with UK, US and **foot length** (not the box "CM" size). Brands with no published chart (e.g. H&M) show EU only.

## Conventions
- Sizes: EU primary (the size printed on the shoe). UK/US/foot length come from the pair's **brand chart** in src/lib/sizes.ts (Nike men's and adidas men's, from nike.com and adidas.com); a pair can override uk/us/cm (and add an optional measured `insole`, cm) under *More size details* in the admin. adidas sells whole sizes and thirds (42, 42 2/3, 43 1/3), all on its chart; an adidas half size (42.5) is not on the chart and shows EU only. Anything without a chart shows EU only.
- Price format "Rs 6,500". Condition is out of 10 with flaws written honestly.
- Pair order = order added (D1 `id`); newest is last in `allProducts` (the site shows newest first).
- Demo pairs are deleted with the *Delete demo pairs* button in /admin. The yellow preview ribbon disappears by itself when no samples remain, a WhatsApp number is set and `returnPolicy` is filled in settings.
- Settings also hold `deliveryFee`, `cities`, `returnPolicy` (empty = neutral placeholder text on the shoe page).
- Keep pages mobile-first (390px) with no horizontal scroll. Check with a phone-width screenshot before committing.
- Photos in admin are shrunk in the browser (1400px, JPEG 85%) before upload; the server accepts JPG/PNG/WebP up to 3 MB, checked by file signature, never by name.
- Local test: copy `.dev.vars.example` to `.dev.vars`, `npm run build && npm run preview`, `npm test`. Delete `.wrangler/state` for a fresh local database.
- Brand SVGs in public/brand were generated from the logo script; regenerate rather than hand-editing.
